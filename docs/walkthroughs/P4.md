# Phase 4 (Backend F, Specialization, and Tiling) Walkthrough & Viva Preparation

## 1. What Was Built
In Phase 4, we built the hardware specialization backend that translates quantized linear operators (`LinearOp`) into synthesizable, bit-exact Verilog-2001 hardware (Design F):

1. **Constant Weight Enforcement (`backend/constant_weights.py`)**:
   - Enforces Invariant I3: only operators with static constant weights (`TensorKind.CONSTANT`) can be synthesized for Design F. Rejects runtime variable or input weights.
   - Provides post-generation RTL verification to ensure no weight input ports or signals exist.

2. **Parametric Matrix Tiling & Zero-Padding (`backend/tiling.py`)**:
   - Decomposes arbitrary weight matrices $(N, K)$ into regular grids of $(N_t, K_t)$ tiles (e.g. $8 \times 16$).
   - Implements clean zero-padding: matrices and activations whose dimensions are not exact multiples of $(N_t, K_t)$ are padded with zeros to $(N', K')$.
   - Produces a deterministic `TileManifest` containing cryptographic SHA256 checksums of the original weights and all individual tile arrays.
   - Mathematically verified reconstruction property: unpadding the accumulated outputs yields 100% bit-identical results to the original matrix multiplication.

3. **Weight Literal & Arithmetic Encoding (`backend/weight_encoder.py`)**:
   - Emits Verilog-2001 signed constants: positive literals as `8'sd<val>` and negative literals as `-8'sd<abs_val>`.
   - Incorporates algebraic simplifications directly into RTL generation:
     - $w = 0$: omitted from accumulation expressions, consuming zero logic gates.
     - $w = +1$: multiplier-free pass-through wire `x_k`.
     - $w = -1$: multiplier-free negation wire `-x_k`.
     - $|w| > 1$: signed 16-bit product wire `wire signed [15:0] prod_... = x_k * weight_literal;`.
   - Explicit 32-bit sign extension: sign-extends 16-bit products using `$signed({{16{prod[15]}}, prod})` prior to addition.

4. **Tile Core Generator (`backend/verilog_codegen.py`)**:
   - Generates standalone combinational Verilog-2001 tile modules (`llmhw_<name>_tile_<t_n>_<t_k>`).
   - Unpacks flat input bus `x_flat` $[8 \cdot K_t - 1 : 0]$ into signed 8-bit slices `x_k`.
   - Computes specialized inner products for all $N_t$ rows.
   - Packs 32-bit accumulator results into `y_flat` $[32 \cdot N_t - 1 : 0]$ with element 0 at the LSBs.
   - Clean compilation under `iverilog -Wall`, `verilator --lint-only -Wall`, and Yosys `check -assert`.

5. **Top-Level Module Generator & Registered Wrapper (`backend/module_generator.py`)**:
   - Instantiates the 2D grid of tile cores, reduction adder trees over $K$ tiles, and constant bias terms.
   - Wraps the combinational core in a registered timing wrapper with fixed latency $L=1$:
     - Synchronous active-low reset `rst_n` driving only `valid_out <= 1'b0`.
     - Datapath registers `y_flat <= y_comb` on `clk` without reset routing overhead.
   - Clean output unpadding: slices internal accumulator buses to exactly the original $N$ outputs, discarding padding lanes before exporting to the top-level port.

6. **Interface Conformance & Static Weight Audit Engine (`verification/weight_audit.py`)**:
   - Strips comments and inspects RTL source code for compliance with Design F contracts.
   - Strictly enforces zero weight ports, zero `w_*` signals, zero writable memory arrays (`reg [...] mem [...]`), and exact port widths.
   - Verified against negative controls with injected weight ports, signals, memories, and simulation directives.

7. **RTL Generation Determinism & Budgets (`tests/test_determinism.py`, `backend/module_generator.py`)**:
   - Guarantees byte-identical RTL output on repeated runs (identical SHA256 checksums).
   - Omit timestamps and machine-specific file paths.
   - Benchmarked and frozen full $576 \times 576$ layer budget: **0.168s generation time**, **7.33 MB file size** (224,750 lines).

## 2. Answers to P4 Viva Explanation Questions

### Question 1: What does "fixed-weight" mean in the generated Verilog, and how do we prove no weight port exists?

**Meaning of "Fixed-Weight" (Design F)**:
In standard programmable neural network accelerators (such as Design P, systolic arrays, or GPUs), weights are stored in readable/writable memories (SRAM, register files, or block RAMs) and streamed into multipliers via runtime weight input ports (`w_data`, `w_addr`, `w_valid`).

In **Design F (Fixed-Weight)**, the model's trained weights are treated as **compile-time mathematical constants** baked directly into the Boolean logic gates:
1. Every non-zero weight is encoded as a signed literal constant (e.g. `8'sd42` or `-8'sd15`) hardwired directly to one operand of a multiplication or adder tree.
2. Zero-value weights are completely eliminated at code-generation time, generating no wires and no gates.
3. Unit-magnitude weights ($\pm 1$) are synthesized as pure pass-through wires or two's-complement inverter gates, avoiding multiplier hardware entirely.
4. The RTL circuit contains **no weight input ports**, **no weight configuration registers**, and **no runtime weight update mechanism**. The hardware is an immutable, single-purpose application-specific accelerator for that exact model.

**How We Prove No Weight Port Exists**:
We prove the absence of weight ports and weight storage using a three-tier automated verification strategy:

1. **Static AST & Lexical Source Audit (`verification/weight_audit.py`)**:
   - The generated RTL is passed through a static regex/lexer engine that strips all single-line (`//`) and block (`/* */`) comments.
   - It extracts the top-level module's port list and verifies that **only four ports exist**:
     - `clk` (1 bit input)
     - `rst_n` (1 bit input)
     - `valid_in` (1 bit input), `valid_out` (1 bit output)
     - `x_flat` ($8 \cdot K$ bits input)
     - `y_flat` ($32 \cdot N$ bits output)
   - It rejects any port matching `w_*`, `weight_*`, `w_data`, or `w_addr`.
   - It scans all internal declarations and rejects any signal matching `w_*` or any 2D memory array declaration (`reg [...] name [0:...]`).
2. **Negative Control Verification (`tests/test_interface_conformance.py`)**:
   - To guarantee that the auditor is not trivially passing bad code, negative controls inject intentional faults:
     - Injecting `input wire [7:0] w_in` raises `WeightAuditError: Weight ports detected`.
     - Injecting `wire signed [7:0] w_val` raises `WeightAuditError: Weight signals detected`.
     - Injecting `reg signed [7:0] weight_ram [0:15]` raises `WeightAuditError: Weight storage arrays detected`.
   - The test suite verifies that all injected violations are reliably killed.
3. **Logic Synthesis Netlist Inspection (Phase 6/7)**:
   - During Yosys synthesis, we check the synthesized cell count: Design F registers only the valid bit and output data flip-flops. There are zero register cells allocated for weight storage.

### Question 2: How does padding keep results exact?

When matrix dimensions $(N, K)$ are not integer multiples of the hardware tile dimensions $(N_t, K_t)$, the compiler must pad the problem to fit the regular tile grid. Padding preserves 100% bit-exact mathematical results through the following mechanism:

1. **Zero-Padding the Matrix**:
   - The weight matrix $W \in \mathbb{R}^{N \times K}$ is padded with zeros along both dimensions to produce $W_{\text{padded}} \in \mathbb{R}^{N' \times K'}$, where $N' = \lceil N/N_t \rceil \cdot N_t$ and $K' = \lceil K/K_t \rceil \cdot K_t$:
     $$W_{\text{padded}}[n, k] = \begin{cases} W[n, k] & \text{if } n < N \text{ and } k < K \\ 0 & \text{if } n \ge N \text{ or } k \ge K \end{cases}$$
2. **Zero-Padding the Input Activations**:
   - The input activation vector $X \in \mathbb{R}^{1 \times K}$ is padded with zeros along $K$ to produce $X_{\text{padded}} \in \mathbb{R}^{1 \times K'}$:
     $$X_{\text{padded}}[k] = \begin{cases} X[k] & \text{if } k < K \\ 0 & \text{if } k \ge K \end{cases}$$
3. **Mathematical Invariance of Inner Products**:
   - Consider the dot product for any legitimate output channel $n < N$:
     $$Y_{\text{padded}}[n] = \sum_{k=0}^{K'-1} X_{\text{padded}}[k] \cdot W_{\text{padded}}[n, k] = \sum_{k=0}^{K-1} X[k] \cdot W[n, k] + \sum_{k=K}^{K'-1} 0 \cdot 0$$
   - Since all padding terms $k \ge K$ satisfy $X_{\text{padded}}[k] = 0$ and $W_{\text{padded}}[n, k] = 0$, their products are identically $0$.
   - Adding $0$ to an integer accumulator is an exact identity operation ($a + 0 = a$ in $\mathbb{Z}$). Thus, $Y_{\text{padded}}[n] \equiv Y[n]$ with zero error.
4. **Physical Output Slicing**:
   - Dummy output rows $n \ge N$ (created solely to complete the tile height $N'$) compute dummy dot products with zero weights.
   - At the top-level module interface, the generator slices the internal bus:
     ```verilog
     assign y_comb = y_padded[32*out_features-1 : 0];
     ```
   - The padding lanes $n \ge N$ are never exposed on the external `y_flat` port. Downstream logic receives only the exact, unpadded $N$-dimensional vector.
   - Because our encoder omits all zero-weight terms, logic synthesis tools (Yosys) completely prune and eliminate the dummy tile hardware, incurring zero redundant silicon area.

### Question 3: Why can signed/unsigned mixing silently break a MAC?

Mixing signed and unsigned types in hardware description languages (particularly Verilog-2001) is one of the most notorious sources of silent, catastrophic arithmetic corruption.

1. **Verilog Type Coercion Rules (IEEE 1364-2001 §4.5.1)**:
   - In Verilog-2001, if **any** operand in an expression is unsigned, the **entire expression is coerced to unsigned**.
   - If an expression contains a mixture of `wire signed [7:0] a` and an unsigned literal (such as `8'd10` or a plain integer `10` or an undeclared wire), Verilog treats `a` as unsigned!
2. **The Two's Complement Interpretation Failure**:
   - Suppose activation $x = -2$ (encoded in 8-bit signed two's complement as `8'b11111110` = `0xFE`).
   - If multiplied by a weight constant intended to be $+3$:
     - **Signed evaluation**: `-2 * 3 = -6` (in 16-bit signed: `16'hFFFA`).
     - **Mixed/unsigned evaluation**: If $+3$ is written as `8'd3` (unsigned) instead of `8'sd3`, Verilog converts `x` to unsigned $254$ (`8'd254`).
     - The product becomes `254 * 3 = 762` (`16'h02FA`)!
     - Instead of negative six, the circuit produces positive seven hundred sixty-two.
3. **Sign-Extension Corruption in Adder Trees**:
   - When adding a 16-bit negative product to a 32-bit accumulator:
     - If the product wire is declared unsigned (`wire [15:0] prod`), Verilog zero-extends it when widening to 32 bits: `16'hFFFA` becomes `32'h0000FFFA` ($+65,530$).
     - The accumulator gains $+65,530$ instead of subtracting $6$.
   - The error does not trigger any syntax error or compiler warning in standard simulators unless `-Wall` is enabled with strict linter checks.
4. **How Our Architecture Precludes Mixed Arithmetic**:
   - All input ports, internal wires, and output ports are explicitly declared with the `signed` keyword:
     `wire signed [7:0] x_k;`, `wire signed [15:0] prod;`, `wire signed [31:0] acc;`.
   - All literals are explicitly stamped with signed decimal format: `8'sd<val>` or `-8'sd<abs_val>`.
   - All widening operations use explicit sign extension:
     `$signed({{16{prod[15]}}, prod})`.
   - Verified by automated static analysis in `backend/weight_encoder.py` and regression test `tests/test_verilog_codegen.py`.
