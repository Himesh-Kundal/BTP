# Phase 5 (Baseline P) Walkthrough & Viva Preparation

## 1. What Was Built
In Phase 5, we constructed the programmable baseline hardware (Design P and Design P_bus), complete with runtime weight loading infrastructure and differential verification against Design F and the golden reference oracle:

1. **Programmable Baseline Generator (`backend/baseline_p.py`)**:
   - `generate_tile_core_p`: Generates combinational tile cores for arbitrary $(N_t, K_t)$ geometries using generic signed multipliers `x_k * w_nk` and explicit 32-bit sign extension.
   - `generate_full_module_p`: Generates complete top-level module containing a `W_reg` register array of size $N' \times K'$ INT8 registers, a serial write port (`w_we`, `w_addr`, `w_data`), tile cores, reduction adder trees over $K$ tiles, constant bias, and registered wrapper with latency $L=1$.
   - `generate_full_module_p_bus`: Generates the logic-only baseline variant taking weights as a wide primary-input bus `w_flat` $[8 \cdot N' \cdot K' - 1 : 0]$, enabling isolated arithmetic datapath synthesis without register array area overhead.
   - Conforms strictly to Rule N10: identical signal widths between Design F and Design P ($x: 8$, $w: 8$, product: 16, accumulator: 32).

2. **Weight Hex Dumping & Testbench Infrastructure (`backend/vectors.py`, `backend/testbench.py`)**:
   - `write_weight_hex_vectors`: Dumps $N' \times K'$ weights into `w.hex` in row-major order (2 hex characters per signed byte in two's complement).
   - `generate_wrapper_testbench_p`: Emits self-checking Verilog-2001 testbenches that:
     1. Apply synchronous active-low reset `rst_n`.
     2. Execute the weight-load phase: assert `w_we = 1`, stream `w_addr` from $0$ to $N' \cdot K' - 1$ with `w_data = w_mem[addr]`, then deassert `w_we = 0`.
     3. Stream input vectors `x_flat` with `valid_in = 1`.
     4. Check `valid_out == 1` and compare `y_flat` with `y_exp.hex` at latency $L=1$.
     5. Output standard summary: `TB_RESULT CHECKED=<n> MISMATCH=<m> TIMING_ERR=<t>`.

3. **End-to-End Differential Verification (`tests/test_differential_f_p.py`)**:
   - Proves mathematically and empirically that for identical weights and inputs:
     $$Y_F == Y_P == Y_{\text{ref\_int64}}$$
   - Verified across 5 diverse matrix and tile geometries:
     1. Toy shape ($1 \times 3$, tile $1 \times 3$)
     2. Symmetric square multiple shape ($8 \times 8$, tile $4 \times 4$)
     3. Rectangular multiple shape ($16 \times 32$, tile $8 \times 16$)
     4. Non-multiple shape ($5 \times 11$, tile $4 \times 4$ padded to $8 \times 12$)
     5. Real SmolLM2 Layer 0 `q_proj` slice ($8 \times 16$ tile)
   - Negative control verified: corrupting weights in P immediately fails verification.

## 2. Answers to P5 Viva Explanation Questions

### Question 1: How does Design P ensure fair evaluation against Design F (Rule N10)?

Fair comparison is a cornerstone of rigorous scientific evaluation. If the baseline architecture had differing bit widths, different pipelining, or different arithmetic assumptions, any area or delay advantage claimed by Design F could simply be an artifact of mismatched specifications rather than true model specialization.

Design P ensures strict fairness through the following architectural guarantees:

1. **Rule N10 Identical Bit-Width Mandate**:
   - Both Design F and Design P use identical signed 8-bit inputs ($x \in [-128, 127]$).
   - Both use identical signed 8-bit weights ($w \in [-127, 127]$).
   - Both compute identical signed 16-bit intermediate products (`wire signed [15:0] prod = x * w`).
   - Both sign-extend products into identical 32-bit accumulators (`$signed({{16{prod[15]}}, prod})`).
   - Both produce identical 32-bit output buses (`[32*N'-1:0] y_flat`).
2. **Identical Tiling & Topological Hierarchy**:
   - Design F and Design P share the exact same $(N_t, K_t)$ tiling grid, the same adder trees over $K$ tiles, and the same constant bias addition circuits.
3. **Identical Timing & Registered Wrapper**:
   - Both designs have identical pipeline latency $L=1$ clock cycle.
   - In both designs, the output data register is clock-gated on `if (valid_in)` to avoid spurious toggling, and the valid register is reset by `rst_n`.
4. **Synthesis Script Equivalence**:
   - When synthesized in Yosys, both designs are processed using identical synthesis scripts, identical optimization passes (`prep; check -assert`), identical target gate libraries, and identical flattening settings.

### Question 2: What are the two variants of Design P (`P` vs `P_bus`) and why are both necessary for synthesis evaluation?

When comparing a fixed-weight ASIC (Design F) against a programmable processor or accelerator (Design P), there are two distinct physical questions:
1. *How much silicon area is saved by eliminating weight memory?*
2. *How much silicon area is saved by replacing generic runtime multipliers with constant-coefficient logic?*

To isolate and answer both questions cleanly, we generate two baseline variants:

1. **Design P (Complete Programmable Accelerator with Storage)**:
   - Contains an internal `W_reg` flip-flop array storing all $N' \times K'$ INT8 weights.
   - Includes a write port (`w_we`, `w_addr`, `w_data`) and decoding logic.
   - **Evaluation Purpose**: Represents a self-contained programmable accelerator tile. Comparing Design F against Design P measures the **total system savings**, which includes both eliminating weight storage flip-flops and simplifying multiplier logic into constant gates.
2. **Design P_bus (Logic-Only Arithmetic Baseline)**:
   - Weights are supplied from an external primary-input bus `w_flat` $[8 \cdot N' \cdot K' - 1 : 0]$ connected directly to the tile multiplier inputs.
   - Contains **zero internal weight registers** and no write decoding logic.
   - **Evaluation Purpose**: Evaluates **pure arithmetic logic efficiency**. Because `P_bus` contains only generic multipliers and adder trees, comparing Design F against `P_bus` isolates the exact gate-level area difference between generic multipliers ($X \times W$) and constant-coefficient arithmetic ($X \times \text{const}$).
   - This ensures that our claims do not inflate the advantage of constant specialization by solely crediting register savings.

### Question 3: How does the weight loading protocol work in Design P, and how does the self-checking testbench synchronize without false timing errors?

**Weight Loading Protocol**:
1. At time $t=0$, `clk`, `rst_n`, `valid_in`, and `w_we` are initialized to 0.
2. Reset is pulsed low for 20 ns (2 clock cycles) and deasserted (`rst_n = 1`).
3. The testbench enters the **Weight-Load Phase**:
   - For each weight address $a \in [0, N' \cdot K' - 1]$:
     - On `@(posedge clk); #1;`, the testbench drives `w_we = 1`, `w_addr = a`, and `w_data = w_mem[a]`.
     - The DUT registers `w_data` into `W_reg[a]` on the subsequent clock edge.
4. After all $N' \cdot K'$ weights are written:
   - On `@(posedge clk); #1;`, the testbench drives `w_we = 0`, `w_addr = 0`, `w_data = 0`.
5. The testbench enters the **Inference Phase**:
   - On each subsequent `@(posedge clk); #1;`, `valid_in = 1` is driven with `x_flat`.

**Testbench Synchronization & Avoiding False Timing Errors**:
A common defect in hardware testbenches is race conditions between the driver and monitor processes during multi-phase protocols:
1. If the checking process begins monitoring `valid_out` too early (during weight loading), it flags spurious `TIMING_ERR` because `valid_out` is zero while weights are being loaded.
2. If the checking process polls `valid_in` with a naive `while (valid_in !== 1'b1)` loop, it can accidentally consume the first posedge of `clk` after `valid_in` was asserted, causing the checking process to be 1 cycle ahead of the actual pipeline latency and falsely comparing Vector 1's expected output against Vector 0's actual output.

**Our Robust Synchronization Solution**:
The checking process in `generate_wrapper_testbench_p` synchronizes through explicit event sequencing:
```verilog
    initial begin
        @(posedge rst_n);
        // 1. Wait for weight-load phase to start and complete
        @(posedge w_we);
        @(negedge w_we);

        // 2. Wait for the clock cycle where Vector 0 is presented
        @(posedge clk);

        // 3. For each vector, wait 1 cycle (latency L=1) and check output
        for (vec_out_idx = 0; vec_out_idx < NUM_VECTORS; vec_out_idx = vec_out_idx + 1) begin
            @(posedge clk);
            #1;
            if (valid_out !== 1'b1) timing_err_count = timing_err_count + 1;
            // Compare y_flat against y_mem[vec_out_idx]
            ...
        end
    end
```
- `@(negedge w_we)` guarantees that the checking process waits until the entire weight table is loaded.
- `@(posedge clk)` aligns the monitor with the cycle when `valid_in` and Vector 0 are driven into the DUT.
- The inner loop then checks `valid_out` and `y_flat` on each subsequent cycle `@(posedge clk); #1;`, exactly matching the manifest latency $L=1$.
- This guarantees zero false timing errors and bit-exact vector alignment.
