4. **Artifact Dumper (`frontend/artifact_dumper.py`)**: Dumps layer weights as NumPy arrays (`weight.npy`) and structured metadata (`meta.json`) including SHA256 checksums to verify tamper-proof reproducibility.
5. **Activation Capture (`frontend/activation_capture.py`)**: Attaches PyTorch forward hooks to record real calibration activations on fixed prompts with deterministic seed 42. Verified bit-exact reproduciblity on rerun.
6. **Frontend Mathematical Validation (`tests/test_frontend_validation.py`)**: Validates across all 7 projection types on layers 0, 14, and 29 that `X @ W.T` matches PyTorch's native layer output within max absolute error $\le 10^{-5}$ (empirical error $\approx 10^{-7}$).
7. **Architectural Layering Compliance (`tests/test_layering.py`)**: Enforces Rule 5 by inspecting ASTs of `ir/`, `compiler/`, `backend/`, and `verification/` to guarantee no model-specific imports (`torch`, `transformers`) or hardcoded model identifiers leak across the frontend boundary.

## 2. Answers to P2 Explain-It Questions

### Question 1: Why does `X @ W.T` reproduce the Linear layer?
In standard linear algebra textbooks, vectors are traditionally written as column vectors $x \in \mathbb{R}^{K \times 1}$, and matrix multiplication is expressed as:
$$y = W x$$
where $W \in \mathbb{R}^{N \times K}$ has $N$ rows (output features) and $K$ columns (input features).

However, in modern deep learning frameworks (including PyTorch), activations are organized in row-major batches:
$$X \in \mathbb{R}^{B \times S \times K}$$
where $B$ is batch size, $S$ is sequence length, and $K$ is the feature dimension (`in_features`).

PyTorch's `nn.Linear(in_features=K, out_features=N)` stores its weight parameter `weight` as a 2D tensor of shape `(out_features, in_features)` (i.e. $N \times K$). To compute the output $Y \in \mathbb{R}^{B \times S \times N}$, the row vectors of $X$ must be multiplied by column vectors of $W$. Because $W$ has shape $N \times K$, it must be transposed to $K \times N$:
$$Y = X W^T + b$$
In NumPy, computing `X @ W.T` computes this exact inner product between each activation token and each output projection weight vector. Our validation tests confirm that dumping PyTorch weights as $N \times K$ float32 arrays and executing `X @ W.T` produces outputs matching PyTorch's internal C++/BLAS kernel within numerical roundoff tolerance ($\sim 10^{-7}$).

### Question 2: What would change with biases?
If a linear projection includes an additive bias $b \in \mathbb{R}^{N}$, PyTorch's forward function evaluates:
$$Y = X W^T + b$$
In Python/NumPy, $b$ is broadcast along the preceding batch and sequence dimensions ($B \times S \times N$).

In SmolLM2-135M, all 210 linear layers have `bias=False`, meaning no bias parameters exist in the pretrained model weights. However, per specification contract Rule $N_5$ (`docs/02` §3), our compiler supports synthetic/optional biases for generality:
1. **Frontend**: Must extract and dump `bias.npy` of shape `[N]` alongside `weight.npy`.
2. **Quantization**: Bias must be quantized into the INT32 accumulator domain. Since activation is scaled by $s_x$ and weight row $n$ is scaled by $s_w[n]$, the product accumulator represents values with scale $s_x \cdot s_w[n]$. Therefore, the bias must be scaled by:
   $$s_b[n] = s_x \cdot s_w[n]$$
   $$b_q[n] = \text{round}(b[n] / s_b[n])$$
   clamped to 32-bit signed integers.
3. **RTL Codegen**: The accumulator tree in the hardware core must initialize its sum with the constant $32\text{'sd}b_q[n]$ instead of zero before accumulating the dot products.
