## 2. Answers to Phase 6 Viva Explanation Questions

### Question 1: Why is mutation testing necessary if we already test on real weights and activations?

**Answer:**
Testing with real model weights and captured activations proves that the hardware computes the intended mathematical function for the target network. However, high test pass rates alone do not prove that the verification testbench itself is capable of catching subtle bugs if the compiler's code generator or RTL templates were corrupted.

Mutation testing deliberately injects synthetic, localized faults (mutants M1–M9) into generated RTL:
1. **Fault Sensitivity Proof:** If an injected mutant (e.g. an off-by-one error in padding lane routing or a dropped product term) passes the testbench, it reveals a blind spot in the verification stimulus.
2. **100% Kill Rate Guarantee:** By proving a 100% kill rate across all 9 categories (0 survivors), we establish that our stimulus (one-hot basis vectors, worst-case sign-aligned vectors, extreme values) exercises every wire, multiplier, sign extension, and pipeline stage.
3. **Timing Independence:** Specifically, mutant M9 (latency contract violation) is killed exclusively by the testbench monitor's synchronous cycle check (`TIMING_ERR`), demonstrating that the harness is strictly sensitive to cycle-level protocol timing.

### Question 2: What are the distinct roles of Verification Levels L0, L1, L2, and L3?

**Answer:**
Verification levels organize testing hierarchically by scope, execution time, and failure diagnostic power:

1. **Level L0 (Toy Models — 1×3, 2×4):**
   - *Role:* Fast sanity check during development and walking skeleton verification.
   - *Characteristics:* Executes in <0.05s on every commit, using small hand-calculated matrices where internal wire values can be trivially inspected by eye.
2. **Level L1 (Synthetic Matrix — Edge Cases & Corner Geometries):**
   - *Role:* Stress-tests corner cases that may not appear in any single transformer layer.
   - *Characteristics:* Non-multiples (e.g. $9 \times 17$, $3 \times 5$), extreme constants ($\pm 127$), accumulator-saturating vectors (sign-aligned worst case), all-zero rows, and synthetic bias near $\pm 2^{20}$.
3. **Level L2 (Real Model Slices — 8×16 Tiles Across 21 Configurations):**
   - *Role:* Proves Claim C1 on the actual weight distribution and calibration scales of SmolLM2-135M.
   - *Characteristics:* Tests all 7 projection types (`q`, `k`, `v`, `o`, `gate`, `up`, `down`) at 3 network depths (early, middle, late).
4. **Level L3 (Multi-Tile Slices — 16×32 with 2×2 Tile Grids):**
   - *Role:* Proves inter-tile spatial composition and reduction adder trees.
   - *Characteristics:* Validates that tile cores with partial sums reduce correctly across multiple tiles along the $K$ dimension without bit truncation.

### Question 3: How does the static weight audit prove Invariant I3 without requiring simulation?

**Answer:**
Simulation tests verify functional input-output behavior, but they do not directly prove structural properties of the synthesized netlist (such as the complete absence of write paths or unauthorized configuration registers).

[`verification/weight_audit.py`](file:///home/himesh/BTP/verification/weight_audit.py) performs a static structural audit:
1. **RTL Constant Extraction:** It parses the generated Verilog source code, identifying multiplier constant expressions (`* 8'sd<w>`, `* -8'sd<w>`, pass-through wires for $+1$, and negate wires for $-1$).
2. **Matrix Reassembly:** It maps these constants back to their $(n, k)$ matrix positions, reconstructing $W_{\text{RTL}}$.
3. **Bit-for-Bit Validation:** It asserts that $W_{\text{RTL}} == W_q$ identically.
4. **Cryptographic Integrity:** It hashes the extracted weights and matches the SHA256 digest against the compiler manifest hash.
5. **Structural Port & Storage Audit (Invariant I3):** It verifies that the module port list contains strictly `ports ⊆ {clk, rst_n, valid_in, x_flat, valid_out, y_flat}`, with zero `w_*` signals, zero write-enable lines, and zero writable `reg` memory arrays.

This audit executes in under 10 milliseconds and provides mathematical certainty of model specialization.

### Question 4: Why is cross-simulator verification (Icarus Verilog vs Verilator) required?

**Answer:**
Single-simulator testing risks masking subtle hardware bugs due to simulator quirks or non-standard semantics:
1. **Event Scheduling vs Two-State Binary Execution:** Icarus Verilog is a 4-state (`0, 1, x, z`) event-driven interpreted simulator, while Verilator is a 2-state cycle-based compiler that converts Verilog into optimized C++ binaries.
2. **Subtle Race Conditions:** An uninitialized register, improper non-blocking assignment (`<=` vs `=`), or implicit signedness conversion might behave benignly in one simulator but produce mismatches or compilation errors in the other.
3. **Lint-Wall Cleanliness:** Verilator's strict lint parser (`-Wall`) enforces commercial-grade syntax rules, catching width truncations, implicit wire declarations, and unused logic before downstream synthesis.
4. **Bit-Exact Equality:** Demonstrating $Y_{\text{iverilog}} == Y_{\text{verilator}} == Y_{\text{ref\_int64}}$ proves that the generated RTL semantics are universally standards-compliant and independent of EDA vendor tooling.
