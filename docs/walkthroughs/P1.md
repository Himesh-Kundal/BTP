# Phase 1 (Walking Skeleton) Walkthrough & Viva Preparation

## 1. What Was Built
In Phase 1, we constructed the thin, end-to-end "walking skeleton" of the compiler:
1. **IR Layer (`ir/linear.py`)**: Hardware-independent dataclass `LinearOp` representing a linear layer with invariants $I_1$ (shape consistency) and $I_2$ (quantized weights strictly within $[-127, 127]$).
2. **Fixed-Weight RTL Codegen (`backend/codegen.py`)**: Pure Verilog-2001 code generator that bakes INT8 weights into the datapath as compile-time constants. Operates with explicit signed arithmetic (`8'sd`, `16'sd`, `32'sd`), explicit sign-extension, zero-weight term pruning, and exposes **no runtime weight ports**.
3. **Integer Reference Oracle (`verification/reference.py`)**: Independent NumPy INT64 golden oracle.
4. **Hex Vector Serialization & Testbench (`backend/vectors.py`, `backend/testbench.py`)**: Automatically produces `x.hex`, `y_exp.hex` and a self-checking testbench reporting `TB_RESULT CHECKED=<n> MISMATCH=<m> TIMING_ERR=<t>`.
5. **Simulation Runner & Mutation Engine (`verification/simulator.py`, `verification/mutate.py`)**: Compiles and simulates via Icarus Verilog (`iverilog`/`vvp`), verifies negative controls, and subjects generated RTL to text-level faults ($M_1$ sign-flip, $M_2$ weight +1, $M_3$ term drop).
6. **Demo Command (`make demo-toy`)**: Single command executing end-to-end compilation, simulation, and 100% mutant kill verification.

## 2. Answers to P1 Explain-It Questions

### Question 1: Why is a testbench that checks zero vectors dangerous?
A testbench that checks zero vectors (or an unasserted loop) can produce a false "green" status without verifying any functional logic. If an uninitialized or broken loop runs 0 iterations, no mismatches occur (`MISMATCH == 0`), misleading automated CI into reporting success. 
In our design, this is prevented by the strict **`CHECKED == expected_count`** contract (enforced in `verification/simulator.py`). If `CHECKED == 0` or does not match the exact number of vectors provided, the simulation immediately fails.

### Question 2: What does a mutation test prove that passing tests cannot?
Passing tests only prove that the circuit matches expected values on the tested inputs. They do *not* prove that the test suite itself is sufficiently thorough to catch bugs. A test suite could pass simply because the assertions are tautological or trivial.
Mutation testing deliberately injects faults into the generated RTL (e.g. flipping a sign $M_1$, perturbing a weight $M_2$, or dropping a sum term $M_3$). If a mutant survives (i.e. the test suite still reports PASS), it proves that the tests are blind to that failure mode. Achieving a **100% kill rate** proves that the test vectors actively exercise and verify every weight, sign, and adder stage in the hardware.
