## 2. Answers to Phase 8 Viva Defense & Technical Questions

### Question 1: How does the unified CLI (`llmhw`) decouple model-specific frontend code from the compiler core while maintaining automated verification?

**Answer:**
A central architectural requirement of the project is Golden Rule 5 (Strict Layering): `ir/`, `compiler/`, `backend/`, and `verification/` must remain completely model-agnostic, never import PyTorch, and never contain hardcoded references to specific models like SmolLM2.

The unified CLI [`cli.py`](file:///home/himesh/BTP/cli.py) enforces this through clean interface contracts:
1. **Frontend Isolation (`llmhw extract`)**: All PyTorch imports and HuggingFace dependencies are confined to `frontend/extractor.py`. The extraction stage outputs a generic `manifest.json` and raw binary or NumPy arrays containing dimension metadata ($N, K$) and signed INT8 weights.
2. **Intermediate Representation Hand-off (`llmhw compile`)**: The compiler takes the serialized manifest and converts it into pure Python/IR data structures (`ir/manifest.py`). The RTL generator emits standard Verilog-2001 using constant-propagation passes.
3. **Model-Agnostic Verification (`llmhw verify`)**: The verification runner takes the generated Verilog and an arbitrary input matrix $X$, executes an independent reference calculation in pure NumPy INT64 ($Y = X \cdot W^T$), and runs a dual-check:
   - Behavioral Verilator simulation with cycle-accurate handshakes.
   - Static regex/AST weight audit verifying that all values in the compiled RTL match the manifest and that zero runtime weight ports exist.
By keeping these stages decoupled via file and data manifests, any modern LLM architecture (LLaMA, Mistral, Gemma) can be supported simply by changing the extractor arguments without modifying a single line of RTL generation or verification logic.

### Question 2: How is fresh-clone reproducibility guaranteed if weight binaries are excluded from version control?

**Answer:**
Trained neural network weights can easily exceed repository storage limits and git history quotas. In accordance with standard open-source practice, raw artifacts and weights in `artifacts/` are gitignored.

However, Gate G8 mandates that a fresh clone in a clean environment must run `make demo` successfully out of the box. To solve this without ballooning repository size, we implemented a dual-fallback architecture:
1. **Fallback Detection (`ensure_layer0_artifacts`)**: When `make demo` or `scripts/run_multi_layer_demo.py` is executed, the script checks if `artifacts/layer_0/weights_manifest.json` exists.
2. **Deterministic On-Demand Extraction**: If missing, the script automatically triggers `frontend/extractor.py` using HuggingFace's `HuggingFaceTB/SmolLM2-135M` checkpoint pinned to exact commit `93efa2f097d58c2a74874c7e644dbc9b0cee75a2`. It extracts layer 0 projections in under 6 seconds and writes them to local storage.
3. **Committed Golden Verification Artifacts**: To eliminate any network or external API dependency during offline evaluation, `results/demo_layer0.json` and `results/demo.json` are committed to the repository. If offline reproduction without HuggingFace access is needed, the pre-recorded verification records can be immediately audited.
This was empirically verified by cloning into `/tmp/llmhw_fresh_clone`, where `make demo` extracted layer 0 and verified all 7 projections in **9.23 seconds**.

### Question 3: How does the project enforce Golden Rule 1 (Zero Unsourced Numbers) across the 40+ numerical claims in the thesis?

**Answer:**
In many engineering theses, numbers cited in the text drift from actual simulation or synthesis logs due to code updates, resulting in unsourced or hallucinated figures.

In this project, numerical integrity is enforced by an automated audit pipeline:
1. **Traceability Matrix ([`docs/report_traceability.md`](file:///home/himesh/BTP/docs/report_traceability.md))**: Every single numerical claim in [`docs/report.md`](file:///home/himesh/BTP/docs/report.md) is registered in a tabular matrix containing:
   - Item Tag (e.g. `A-01` through `T-02`).
   - Claim Description and Exact Cited Value.
   - Source Artifact Link (e.g. `results/E1.csv`, `results/E2.csv`, `results/E5.json`).
   - Command used to generate the result.
   - Verification Status (`VERIFIED` or `ESTIMATE`).
2. **Automated CI Validation ([`tests/test_report_traceability.py`](file:///home/himesh/BTP/tests/test_report_traceability.py))**:
   - The test parses both `docs/report.md` and `docs/report_traceability.md`.
   - It cross-references every cited number directly against the underlying JSON or CSV data in `results/`.
   - If a source file is missing or a number deviates, `make check` fails immediately.
3. **Explicit Estimation Labeling**: Any value that is not directly measured on synthesized gates (such as full-layer cell counts extrapolated from tile sums) is required to carry an explicit `(estimate)` tag in the text and report table.

### Question 4: How does the multi-tile RTL generator achieve sub-second generation times for full-layer dimensions ($576 \times 576$, 331,776 weights)?

**Answer:**
Scaling from a single $8 \times 16$ tile (128 weights) to a full SmolLM2-135M projection ($576 \times 576$, 2,592 tiles, 331,776 weights) produces over 548,000 lines of synthesizable Verilog (30.02 MB). Naive string concatenation or AST-based graph generation in Python often takes tens of seconds or minutes for circuits of this magnitude.

The backend generator achieves sub-second performance (**0.54 seconds**) through targeted design decisions:
1. **Streaming String Buffers**: The generator avoids intermediate tree manipulation or repetitive memory allocations. It iterates through the tile matrix using contiguous NumPy array slicing and formats Verilog instance blocks directly into large pre-allocated string buffers.
2. **Hierarchical Modularity**: Rather than emitting a monolithic flattened Verilog module with 331,776 unrolled expressions, the generator emits modular tile submodules (`tile_r{i}_c{j}`) and instantiates them in a clean top-level grid accompanied by an inter-tile adder reduction tree.
3. **Fast Weight Audit via Regex Tokenization**: In Task T8.3, the static weight auditor verifies that all 331,776 constants match the original FP32-to-INT8 tensor in **0.85 seconds** by leveraging compiled regex tokenizers and vectorized NumPy array equality checks.
This ensures that the hardware compilation pipeline can be integrated into rapid continuous-integration cycles and interactive compilation flows.
